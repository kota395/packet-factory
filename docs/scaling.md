# サービスが大量のリクエストを捌けるようになるまで

ゲームの拡張の土台として(ゲームの作りとは独立した考え方として)、実際の Web サービスがどういう順番で処理能力を伸ばしていくかを整理する。
各段階で「何が詰まるか → どう手を打つか → 次にどこが詰まるか」を並べ、最後にゲームでの表現をまとめる。

## リクエストの通り道

```
ユーザー → [CDN] → [LB] → WEB(アプリ) → [キャッシュ] → DB(プライマリ / リードレプリカ)
  エッジ     入口      計算                  読み込みの近道     データ
```

| 層 | 役割 | 状態を持つか | 増やし方 |
| --- | --- | --- | --- |
| エッジ(CDN) | 画像・動画などの静的データを利用者の近くで返す | 持つ(コピー) | 事業者の網を借りる。回線と容量を買う |
| 入口(LB) | 後ろのサーバーへ振り分ける | 持たない | 基本 1 組。回線と性能を上げる |
| 計算(WEB) | ページを組み立てる。必要なときだけ後段へデータを取りに行く | 持たない(ステートレス) | 何台でも並べられる |
| キャッシュ | よく読まれるデータをメモリに置き、DB へ行かせない | 持つ(消えてもよいコピー) | 台数・容量を増やす |
| データ(DB) | データの正本を持つ | 持つ(正本) | 簡単には増やせない(下の段階 3〜5) |

ポイントは「**状態を持たない層は並べるだけで増やせるが、状態を持つ層は増やし方に工夫がいる**」こと。
拡張の歴史は、詰まりを状態を持たない層へ逃がしていく過程と言える。

## 段階

### 段階 1: 1 台構成

- 構成: サーバー 1 台がすべてを処理する
- 詰まる所: CPU(同時に処理できる数)
- 打ち手: **スケールアップ**(より高性能な機種に入れ替える)
- 限界: 1 台の性能には上限があり、上位機種ほど割高。壊れたら全停止

### 段階 2: 水平分散(スケールアウト)

- 構成: LB を置き、同じ WEB を何台も並べて振り分ける
- 前提: WEB がステートレスであること(ログイン状態などをサーバーごとに持たない)
- 詰まる所: WEB の台数 → 次に LB の帯域(通せるデータ量)
- 打ち手: WEB の増設、LB の回線増強

### 段階 3: データ層の分離

- 構成: 会員機能などデータを保存する機能のために DB を置く。WEB は必要なときだけ DB に問い合わせる
- 特徴: 全リクエストのうち DB まで行くのは一部(ゲームでは WEB に届いた 1/5)
- 詰まる所: DB。WEB をいくら増やしても DB は 1 台なので、ここに集中する
- 打ち手: DB のスケールアップ。DB は正本を持つので、WEB のように「並べて振り分ける」ことはできない

### 段階 4: 読み込みの分散

実際のサービスでは読み込みが書き込みよりずっと多い(8:2〜99:1)。そこで読み込みだけを逃がす。

- **キャッシュ**: 同じデータを何度も DB に取りに行かないよう、メモリに置いて返す。当たった分は DB に届かない
- **リードレプリカ**: DB(プライマリ)の複製。読み込みはレプリカに分散できる。書き込みはプライマリだけが受ける
- 代償: レプリカはプライマリの書き込みを反映(レプリケーション)し続けるので、書き込みが多いとレプリカも忙しくなる
- 詰まる所: 書き込みを一手に受けるプライマリ。**冗長化(台数で分散)できるのは読み込みだけ**

### 段階 5: 重いコンテンツの配信

- 状況: 画像・動画でリクエスト 1 件あたりのデータ量が何倍〜何十倍にもなる
- 詰まる所: CPU より先に帯域(LB の回線)
- 打ち手: **CDN**(エッジでキャッシュして返し、LB より後ろに流さない)、LB の回線増強

### 段階 6: 書き込みの分散(シャーディング)

- 構成: データをユーザー ID などで分割し、複数のプライマリに分けて持つ。書き込みもスケールアウトできる
- 代償: シャードをまたぐ処理が難しくなり、運用も重い(ゲームでは価格の重さで表現)

### 今後の段階(未実装)

| 段階 | 内容 |
| --- | --- |
| 非同期化 | キュー + ワーカー。動画の変換や通知など重い処理をリクエストの外へ逃がし、バーストを吸収する |
| オブジェクトストレージ | 画像・動画の実体を WEB から切り離し、CDN の取得元にする |
| 複数の LB / マルチリージョン | LB の接続先(64 台)を越えて広げる。障害(サーバー故障・リージョン障害)に備えて複数拠点で動かす。障害イベントと組み合わせる |

## ゲームでの表現

ラックと配線の版(現在)での表現は [design.md](design.md) を参照。
ここに書いた段階のうち、今のゲームにあるのは「1 台構成 → 役割の分離(LB と web の並列)→ キャッシュ(memcached)→ 増床(ラック間・集約スイッチ)」まで。
リードレプリカ・CDN・シャーディングは、物理層の上でもう一度作り直す予定。
