# サービスが大量のリクエストを捌けるようになるまで

ゲームの拡張の土台として、実際の Web サービスがどういう順番で処理能力を伸ばしていくかを整理する。
各段階で「何が詰まるか → どう手を打つか → 次にどこが詰まるか」を並べ、最後にゲームでの表現をまとめる。

## リクエストの通り道

```
ユーザー → [CDN] → [LB] → WEB(アプリ) → [キャッシュ] → DB(プライマリ / リードレプリカ)
  エッジ     入口      計算                  読み込みの近道     データ
```

| 層 | 役割 | 状態を持つか | 増やし方 |
| --- | --- | --- | --- |
| エッジ(CDN) | 画像・動画などの静的データを利用者の近くで返す | 持つ(コピー) | 事業者の網を借りる。回線と容量を買う |
| 入口(LB) | 後ろのサーバーへ振り分ける | 持たない | 基本 1 組。回線と性能を上げる |
| 計算(WEB) | ページを組み立てる。必要なときだけ後段へデータを取りに行く | 持たない(ステートレス) | 何台でも並べられる |
| キャッシュ | よく読まれるデータをメモリに置き、DB へ行かせない | 持つ(消えてもよいコピー) | 台数・容量を増やす |
| データ(DB) | データの正本を持つ | 持つ(正本) | 簡単には増やせない(下の段階 3〜5) |

ポイントは「**状態を持たない層は並べるだけで増やせるが、状態を持つ層は増やし方に工夫がいる**」こと。
拡張の歴史は、詰まりを状態を持たない層へ逃がしていく過程と言える。

## 段階

### 段階 1: 1 台構成

- 構成: サーバー 1 台がすべてを処理する
- 詰まる所: CPU(同時に処理できる数)
- 打ち手: **スケールアップ**(より高性能な機種に入れ替える)
- 限界: 1 台の性能には上限があり、上位機種ほど割高。壊れたら全停止

### 段階 2: 水平分散(スケールアウト)

- 構成: LB を置き、同じ WEB を何台も並べて振り分ける
- 前提: WEB がステートレスであること(ログイン状態などをサーバーごとに持たない)
- 詰まる所: WEB の台数 → 次に LB の帯域(通せるデータ量)
- 打ち手: WEB の増設、LB の回線増強

### 段階 3: データ層の分離

- 構成: 会員機能などデータを保存する機能のために DB を置く。WEB は必要なときだけ DB に問い合わせる
- 特徴: 全リクエストのうち DB まで行くのは一部(ゲームでは WEB に届いた 1/5)
- 詰まる所: DB。WEB をいくら増やしても DB は 1 台なので、ここに集中する
- 打ち手: DB のスケールアップ。DB は正本を持つので、WEB のように「並べて振り分ける」ことはできない

### 段階 4: 読み込みの分散

実際のサービスでは読み込みが書き込みよりずっと多い(8:2〜99:1)。そこで読み込みだけを逃がす。

- **キャッシュ**: 同じデータを何度も DB に取りに行かないよう、メモリに置いて返す。当たった分は DB に届かない
- **リードレプリカ**: DB(プライマリ)の複製。読み込みはレプリカに分散できる。書き込みはプライマリだけが受ける
- 代償: レプリカはプライマリの書き込みを反映(レプリケーション)し続けるので、書き込みが多いとレプリカも忙しくなる
- 詰まる所: 書き込みを一手に受けるプライマリ。**冗長化(台数で分散)できるのは読み込みだけ**

### 段階 5: 重いコンテンツの配信

- 状況: 画像・動画でリクエスト 1 件あたりのデータ量が何倍〜何十倍にもなる
- 詰まる所: CPU より先に帯域(LB の回線)
- 打ち手: **CDN**(エッジでキャッシュして返し、LB より後ろに流さない)、LB の回線増強

### 段階 6: 書き込みの分散(シャーディング)

- 構成: データをユーザー ID などで分割し、複数のプライマリに分けて持つ。書き込みもスケールアウトできる
- 代償: シャードをまたぐ処理が難しくなり、運用も重い(ゲームでは価格の重さで表現)

### 今後の段階(未実装)

| 段階 | 内容 |
| --- | --- |
| 非同期化 | キュー + ワーカー。動画の変換や通知など重い処理をリクエストの外へ逃がし、バーストを吸収する |
| オブジェクトストレージ | 画像・動画の実体を WEB から切り離し、CDN の取得元にする |
| 複数の LB / マルチリージョン | LB の接続先(64 台)を越えて広げる。障害(サーバー故障・リージョン障害)に備えて複数拠点で動かす。障害イベントと組み合わせる |

## ゲームでの表現(抽象化)

### リクエストの種類

| 種類 | 発生する所 | 完了する所 | 単価 |
| --- | --- | --- | --- |
| 静的 | 利用者のリクエストの大部分 | CDN(キャッシュに当たれば)/ WEB | 低い |
| 読み込み | 会員機能の解放後、利用者のリクエストの 1/5 × 8 割 | キャッシュ(当たれば)/ レプリカ / DB | 高い |
| 書き込み | 同上(1/5 × 2 割) | DB(プライマリ)のみ | 高い |

読み込み・書き込みは動的なリクエストなので CDN ではキャッシュできず、必ず WEB まで届く。
CDN がない間は「WEB に届いたうちの 1/5 がデータ層へ行く」のと同じで、CDN を置くと静的だけが減るので WEB に届く分に占める割合は上がる。
WEB にデータ層がつながっていなければ、WEB だけで静的として返す(会員機能が使えないだけで、エラーにはしない)。

### ノードの能力の組み合わせ

ノードの振る舞いは種類ごとの分岐ではなく、`NODE_DEFS` の項目の組み合わせで決まる。新しいノードは定義を足すだけで動く。

| 項目 | 意味 | 使っているノード |
| --- | --- | --- |
| `accepts` / `terminates` | 受け付ける種類 / ここで完了する種類 | 全部 |
| `serviceMs` × `workers` | 処理時間と同時処理数(= 処理の上限) | 全部 |
| `bandwidthMBps` | 帯域。データ量 ÷ 帯域だけ回線を占有する | CDN, LB |
| `cache` | 指定した種類をヒット率の確率でここで返す | CDN(静的), キャッシュ(読み込み) |
| `routePriority` | 振り分け先の優先度。高い先があればそちらだけに送る | キャッシュ > レプリカ > DB(読み込み) |
| `localFallback` | 送り先がない読み込み・書き込みを、エラーにせず静的として返す | WEB |
| `replicatesTo` / `replicaOf` | 書き込みを複製先に反映する / 複製元がないと受け付けない | DB → レプリカ |
| `maxCount` | 置ける台数(強化で増やせる) | CDN, LB, DB |

強化は `target`(対象ノードと能力: 速度・帯域・ヒット率・台数)で効き先を決める。スケールアップには `maxLevel` があり、1 台の性能には上限がある(上限に達したら台数で分散するしかない)。

### 段階と解放

| 段階 | 解放 | 主な強化 |
| --- | --- | --- |
| 1. 1 台構成 | ―(WEB 1 台から開始) | WEB スケールアップ(上限 Lv6) |
| 2. 水平分散 | ロードバランサー | LB 回線増強 |
| 3. データ層の分離 | 会員機能(DB) | DB スケールアップ(上限 Lv8、レプリカにも効く) |
| 4. 読み込みの分散 | キャッシュ、リードレプリカ | キャッシュ容量 |
| 5. 重いコンテンツ | 画像投稿、CDN、動画配信 | CDN キャッシュ・回線 |
| 6. 書き込みの分散 | シャーディング | シャード追加 |

広告と収益化の改善はどの段階でも買える。

### 価格の調整

価格はすべて `src/sim/pricing.ts` にまとめてある。

- `START_MONEY`: 最初の資金
- `PRICE_SCALE`: すべての購入価格に掛かる倍率(全体を一律に高く・安くしたいとき)
- `NODE_PRICES`: ノードごとの 1 台目の価格(`first`)、1 台増やすごとの倍率(`growth`)、維持費(`upkeep`)
- `UNLOCK_PRICES`: 解放の価格
- `UPGRADE_PRICES`: 強化の Lv0 の価格(`first`)と、1 レベルごとの倍率(`growth`)

変えたら `npm run balance` で節目の時刻を確認する。
