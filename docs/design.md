# 設計: ラックと配線から育てるインターネット企業

インターネット企業のインフラ担当として、コロケーションの 1 ラックからサービスを育てるゲーム。
機器の設置場所・電力・スイッチのポート・配線を考え、どこに何を置き、どうつなぐかを最適化していく。

拡張の考え方(サービスがどう詰まり、どう分散していくか)は [scaling.md](scaling.md) にまとめてある。

## 2 つの層

### 物理層: 列・ラック・機器・ポート・ケーブル

| 要素 | 内容 |
| --- | --- |
| 列 | ラックを横に並べた 1 列。最大 20 区画。最初は 1 区画だけ借りている |
| ラック | 42U。ラックごとに電力の上限がある(最初は 2kVA 相当。U より先に電力が詰まることが多い) |
| 機器 | サーバ・スイッチ・回線終端・ストレージアプライアンス。機種ごとに U 数・消費電力・ポートが決まっている |
| ポート | 機器の背面にある。速度(100M / 1G / 10G)と種類(RJ45 / SFP)がある |
| ケーブル | ポートとポートを 1 本でつなぐ。リンク速度は両端の遅い方。長さで値段が変わる(同じラック内は短く、ラック間はケーブルトレイを通るので長い) |

- サーバは機種固定(コア数・コア性能・メモリ・ディスク IOPS・NIC)。スペックを上げる強化はなく、上位機種に買い替えて役割を移す
- 同じ 2 台の機器を複数のケーブルでつなぐと、まとめて 1 本の太いリンクとして扱う(LAG)
- 通信はスイッチだけが中継する。サーバは中継しない
- 回線終端はキャリアの機器で、ラック 1 の一番上に固定。速度は回線契約で決まる(100M → 1G → 10G)

### 論理層: サービスと役割

お題は最初はブログ。投資でショッピング・写真共有・動画配信を始められ、サービスごとにユーザー・市場規模・単価がある。
ブログのページビュー 1 件ごとに次の仕事が発生する。

| 役割 | 仕事 | 主に使う資源 |
| --- | --- | --- |
| web | ページを組み立てて返す(画像を載せると返すデータが重くなる) | CPU、ネットワーク |
| db | 1 ページあたり数回の読み込み、コメント機能のあとは書き込み | CPU、ディスク IO(メモリが少ないとキャッシュに乗らず IO が増える) |
| cache | memcached。db の読み込みを肩代わりする | ほぼネットワーク |
| lb | ロードバランサ(LVS)。複数の web に振り分ける | 少しの CPU、ネットワーク |
| replica | db(プライマリ)の複製。読み込みを肩代わりし、書き込みはすべて複製されて反映する | CPU、ディスク IO |

| search | 商品の検索(ショッピング)。なければ db が LIKE 検索で肩代わりする(重い) | CPU、メモリ(索引が乗らないとディスク IO) |
| media | 画像・動画の配信と保存(写真共有・動画配信)。なければ web が肩代わりする | ネットワーク、ディスク IO |
| worker | 投稿の加工(サムネイル生成・エンコード)。なければ web が肩代わりする | CPU |

- 役割は「サービス:役割」(blog:web、shop:search など)でサーバ(または VM)に割り当てる。1 台に複数の役割を同居できる(最初は blog:web + blog:db の LAMP 1 台)
- サービスを相乗りさせるか分けるかはプレイヤーが決める。同じ機器・リンクを使えば負荷は合算され、db・search・media が同じサーバにいれば残りのメモリ(キャッシュ)を分け合う
- 写真・動画のページは、ページとは別に media から画像・動画を取得する(LB があれば LB 経由で media に振り分け、なければ media 1 台だけが受ける)。投稿は web → worker → media(保存)と流れる
- ショッピングのキャンペーン: お金を払うとすぐ始まり、一定時間 訪問と注文の単価が増える。終わるとクールタイム
- LB がない間、インターネットから届くのは web 1 台だけ(グローバル IP が 1 つ)。web を並べるには LB が要る
- db(プライマリ)は 1 台だけ。読み込みはレプリカ(db から届くもの)に分け、書き込みはプライマリだけが受ける

### 仮想化と共有ストレージ

- サーバを「ハイパーバイザ」にすると、自分は役割を持たず VM を載せる。VM は大きさ(S / M / L = vCPU とメモリ)を選び、役割は VM に付ける
- VM はホストの CPU を分け合い(仮想化のオーバーヘッドあり)、通信はホストの NIC から出入りする。同じホストの VM 同士はネットワークを通らない
- メモリはホストの分(8GB)を除いた残りまで、vCPU はコア数の 2 倍までしか割り当てられない
- VM のディスクはホストのローカルディスクか、共有ストレージ(アプライアンス)に置く。共有ディスクの IO はネットワークを通ってストレージへ行く
- VM を別のホストへ移すとき、ローカルディスクならコピーの間(20 秒)止まる。共有ストレージなら止まらない(ライブマイグレーション)
- ストレージの IO とサービスの通信が同じスイッチ・同じリンクを通ると取り合いになる。ストレージ用のスイッチとホストの 2 本目の NIC で経路を分けると解消する(クロスネットワーク)

## シミュレーション: 流量モデル

機器・ポート・ケーブルが数百〜数千になっても軽く動くよう、パケットを 1 個ずつ流すのではなく、一定間隔ごとに流量から使用率を計算する。

1. ページビュー/秒 = ユーザー数 × 1 人あたりの PV
2. 役割ごとに、どのサーバへどれだけ流れるかを決める(均等に振り分け)
3. 通信ごとにネットワーク上の経路を求め(スイッチ経由の最短経路)、各リンク・各スイッチに流量を積む
4. サーバの CPU・ディスク IO、リンク、スイッチ、回線の使用率を出す
5. 使用率が 1 を超えた資源を通る分は溢れてエラーになる。使用率が高いほど待ち時間が延びて応答が遅くなる
6. 成功したページビューが売上になり、エラーや遅さでユーザーが離脱する

画面では、ケーブルの色と太さが使用率と速度、機器のメーターが CPU・IO を表す。

## 画面と操作

- **列の立面図**: ラックを横に並べて表示。引くと列全体、寄るとラックの U が見える(ドラッグ・ホイール・ピンチ)
- **前面**: 空いている U をタップすると、そこに収まる機器の一覧から購入して設置。機器はドラッグで別の U やラックへ移せる。空き区画をタップするとラックを借りる
- **背面(配線)**: 機器のポートが見える。ポートから別のポートへドラッグでケーブルを引く。ケーブルやポートをタップして抜く
- **サービス**: サービスごとのタブで、役割ごとのサーバと負荷、流れ(回線 → LB → web → cache → db)、詰まりや未接続の警告。ショッピングはキャンペーン
- **メトリクス**: 全体かサービスごとの推移と需要予測
- **投資**: 事業 / 回線・電力 / ソフトウェア / 機器 のタブ

## 時代(段階)

| 段階 | 状況 | 新しく考えること |
| --- | --- | --- |
| 1. 黎明期 | 1 ラック、LAMP 1 台 | 電力・U・ポート。最初に詰まるのは db のディスク IO |
| 2. 役割の分離 | db を大容量メモリの機種へ、web を LB の後ろに並べる | 機種選び、役割の移動、LB |
| 3. キャッシュ | memcached | db の読み込みを逃がす |
| 4. 増床 | 2 ラック目以降、ToR → 集約スイッチ | ラック間の配線、アップリンクの帯域(オーバーサブスクリプション)、配置の最適化 |
| 5. DB の冗長化 | リードレプリカ | 読み込みの分散、複製の通信と反映の負荷 |
| 6. 仮想化 | ハイパーバイザと VM | 大きなホストへの集約(U と電力の節約)、VM の配置(同じホストに置くと通信が速い) |
| 7. 共有ストレージ | ストレージアプライアンス | ライブマイグレーション、ストレージ用ネットワークの分離 |
| 8. ネットワークの冗長化 | BGP(サーバと ToR の間)、ECMP | 2 台の ToR につないで片方が止まっても続ける。BGP なしの機器は配線どおりの 1 本だけで切り替わらない |
| 9. 複数のサービス | ショッピング・写真共有・動画配信 | 相乗りか分離か。検索・画像配信・エンコードという別の詰まり方。キャンペーンの急増に備える |
| 今後 | スパインリーフ、複数列・自社 DC | |

難易度オプション(流量の揺れ・障害)は `config.ts` の `DIFFICULTY`。既定はオフ。
