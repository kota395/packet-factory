# packet-factory

インターネット企業のインフラ担当として、コロケーションの 1 ラックからサービスを育てるブラウザゲーム。
機器の設置場所・ラックの電力・スイッチのポート・配線を考え、どこに何を置き、どうつなぐかを最適化していく。
GitHub Pages などの静的ホスティングだけで動く。

**遊ぶ: https://kota395.github.io/packet-factory/**

> ステータス: ラックと配線の版(黎明期 → 役割の分離 → キャッシュ → 増床 → DB の冗長化 → 仮想化 → 共有ストレージ → ネットワークの冗長化 → 複数のサービス → コンテナ → シャーディング → 回線の多重化と CDN。お題はブログ・ショッピング・写真共有・動画配信)
>
> 設計は [docs/design.md](docs/design.md)、サービスの拡張の考え方は [docs/scaling.md](docs/scaling.md)、
> 技術選定とライセンス方針は [docs/tech-stack.md](docs/tech-stack.md) を参照。

## 遊び方

- 最初はラック 1 本に、回線終端(100Mbps)・L2 スイッチ・リクエストを受ける 1U サーバ(web)・db 用の 2U サーバ(HDD)が入っている
- ユーザー数 × 0.01 がページビュー/秒になり、捌けた分だけ収入になる。溢れるとエラーになり、ユーザーが離れる
- 1 ページビューで、web がページを組み立て、db に 3 回読み込みに行く。画像投稿を入れると返すデータが 6 倍、コメント機能を入れると db に書き込みが来る
- 投資で新しいサービスを始められる(ブログ → ショッピング → 写真共有 → 動画配信)。ユーザー・市場規模・単価はサービスごと。役割はサービスごとに付けるので、同じサーバに相乗りさせても、サーバやラックを分けてもよい
  - ショッピング: 単価が高い。商品の検索(search。なければ db が重い LIKE 検索で肩代わり)と、注文の書き込み(db のプライマリだけ)。キャンペーンを打つとすぐ始まり、90 秒間 訪問が 2.5 倍になる(終わると 5 分は打てない)
  - 写真共有: 1 ページにサムネイルが 12 枚並び、画像の配信(media)で帯域とディスク IO を使う。投稿された写真のサムネイル生成(worker)は CPU を食う。media・worker がなければ web が肩代わりする
  - 動画配信: 配信の帯域が桁違い。投稿のエンコード(worker)は 1 本で CPU を 60 秒使う
- サーバはシャーシ(1U / 2U)に CPU・メモリ・ドライブ・NIC を載せた構成。買うときはプリセットから選び、あとから詳細でワンクリックで替えられる(外したパーツは半額で下取り)
  - 1U: 前面に 2.5 インチ 10 本(SSD・NVMe を混ぜられる)。最初は SSD 2 本のミラー
  - 2U: 前面は 3.5 インチ HDD 12 本か、2.5 インチ 24 本(SSD・NVMe を混ぜられる)。背面に OS 用の SSD 2 本(ミラー)
  - ドライブは 2 本ずつのミラーで、IO 性能は本数と種類で決まる(容量は扱わない)。HDD < SSD < NVMe(NVMe は投資で解放)
  - CPU はコア数が多いほど 1 コアあたりの電力と価格が下がる。電力はシャーシとパーツの合計
- ラックには電力の上限がある(最初は 2kW)。U より先に電力が詰まりやすい
- ページを閉じている間も、直前の収支の 50% を最大 8 時間分受け取れる。進行はブラウザに自動保存される

### 操作

| 画面 | 操作 |
| --- | --- |
| 前面 | 空いている U をタップ → サーバの構成(プリセット)か機種を選んで設置(2U の機器はタップした U から上に 2U)。機器をドラッグで別の U やラックへ移動。ハイパーバイザにはサービスごとの VM の台数が出る。点線の区画をタップしてラックを借りる |
| 背面 | ポートから別のポートへドラッグして配線(線が指に追従し、長さと値段が出る)。ケーブルやポートをタップすると詳細と「抜く」 |
| 機器の詳細 | サーバの構成(CPU・メモリ・ドライブ・前面のバックプレーン・増設 NIC をワンクリックで替える)、役割の割り当て(始めたサービスごとに lb / web / cache / db / replica、ショッピングは search、写真・動画は media / worker)、ハイパーバイザにする、VM を作る、BGP、メンテナンス、負荷、ポートのつながり、売却 |
| VM の詳細 | 役割、ディスク(ローカル / 共有ストレージ)、別のホストへ移す、消す |
| サービス | サービスごとのタブで、流れ(回線 → lb → web → cache → db など)、警告、役割ごとのサーバ、仕事量、収支の内訳。ショッピングのタブからキャンペーンを打てる |
| 投資 | 事業(広告・収益化・新しいサービス・キャンペーン)、回線・電力、ソフトウェア、機器のタブ |
| メトリクス | 上の「メトリクス」ボタン。全体かサービスごとに、ページビュー・キャパシティ・余裕・需要がキャパシティに届くまでの時間などの数値と、需要とキャパシティ(予測つき)・ユーザー数・資源の使用率(上位 5)・エラー率・応答・収支の推移。期間は 5 分 / 15 分 / 1 時間 |
| 共通 | 空いている所のドラッグ・ホイール・ピンチで見る範囲を動かす。左上の ＋ − ⤢ |

ルール:

- 通信はスイッチだけが中継する(サーバは中継しない)。同じ 2 台を複数のケーブルでつなぐと束ねて 1 本の太いリンクになる
- スイッチは最短の経路が複数あれば均等に分ける(ECMP)。サーバなど端の機器は、BGP を使わなければ配線どおりの 1 本(一番若いポート側)だけを使い、その先が止まっても切り替わらない。BGP を使うと(物理サーバは詳細でオン、ハイパーバイザは自動)生きている隣すべてに ECMP で流れ、片方が止まっても続く
- 機器は詳細から「メンテナンスで止める」ことができる。障害(機器がときどき止まる)は難易度オプションで既定はオフ(`config.ts` の `DIFFICULTY.failures`)
- リンクの速度は両端のポートの遅い方。回線終端の速度は回線契約で決まるが、つないだ先のポートが 1G なら 1G まで
- LB がない間、インターネットから届くのは web 1 台だけ
- db(プライマリ)は最初は 1 台だけで、読み込みはレプリカに分けられる。書き込みは 1 台が上限なので、「DB の機能分割」で 2 台(1 台目が主なデータ、2 台目が書き込みの多いデータで書き込みはすべてこちら)、「シャーディング」で何台にでも等分できる。データが分かれるとメモリに乗りやすくなる。レプリカは順番にそれぞれの db の複製になる
- 回線は 1 本(最大 10G)。「回線の多重化」で回線終端を前面から買い足すと、BGP で回線に均等に分かれ、1 本止めても残りで続く(月額は本数ぶん)
- 「CDN」を入れると、ブログの画像と写真・動画の配信の 9 割を CDN が配り、オリジンの回線とサーバを通らない。配った量に応じて従量課金
- db とレプリカはサーバのメモリが少ないと読み込みがディスクに行き、ディスク IO が詰まる
- ハイパーバイザに VM を載せると、同じホストの VM 同士の通信はネットワークを通らない。VM はホストの CPU を分け合う
- Kubernetes: サーバか VM を「ワーカー」にし、サービスの詳細で役割(web・cache・search・worker)を Deployment にすると、Pod(1 vCPU・2GB)がワーカーに分散して自動で置かれる。Pod の数は CPU 60% を目標に自動で増減する(VM は手で作るまま)。ワーカーが止まると Pod は残りのワーカーに置き直される。db・replica・media はサーバか VM で動かす
- LB がなくても、BGP を使うワーカー(物理サーバは BGP をオン、ハイパーバイザ上の VM は自動)の web の Pod は、インターネットから直接受けられる(MetalLB)
- VM のディスクを共有ストレージに置くと止めずに別のホストへ移せる(ローカルだと 20 秒止まる)。IO はネットワークを通るので、ストレージ用のスイッチと NIC で経路を分けたくなる

### 段階

| 段階 | 状況 | 打ち手 |
| --- | --- | --- |
| 1. 黎明期 | web 1 台と db 1 台。db の HDD のディスク IO が詰まる | db のメモリを増やし、SSD に替える |
| 2. 役割の分離 | web の CPU が詰まる | LB を入れ、web を並べる。LB サーバの NIC も詰まる |
| 3. キャッシュ | db の読み込みが多い | memcached |
| 4. 増床 | 電力・ポート・スイッチ間の帯域が詰まる | 2 本目のラック、10G スイッチ、集約スイッチ、リンクを束ねる |
| 5. DB の冗長化 | db の読み込み | リードレプリカ(書き込みは全レプリカに複製される) |
| 6. 仮想化 | U と電力、台数の管理 | 大きなホストに VM をまとめる |
| 7. 共有ストレージ | VM を止めずに動かしたい | ストレージアプライアンス、ストレージ用ネットワーク |
| 8. ネットワークの冗長化 | スイッチ 1 台で全部止まる | BGP を解放し、サーバを 2 台の ToR につないで ECMP |
| 9. 複数のサービス | サービスが増えると負荷の形が変わる(検索・画像配信・エンコード、キャンペーンの急増) | 相乗りか分離かを決める。search・media・worker を専用のサーバへ |
| 10. コンテナ | サービスごとに台数を手で合わせるのが大変 | Kubernetes のワーカーに Pod を自動配置・オートスケール。BGP で LB なしに受ける |
| 11. シャーディング | db の書き込みが 1 台の上限に当たる | 機能分割、シャーディング |
| 12. 回線の多重化と CDN | 回線 10G が上限 | 回線を増やして BGP で分ける、画像・動画を CDN へ |

### 進行の目安(バランス確認ボットの結果)

| 時間 | 出来事 |
| --- | --- |
| 8〜9 分 | db を 1U(2 CPU)へ移す |
| 10〜11 分 | LB を入れて web を並べ始める |
| 15〜17 分 | 回線契約 1G、画像投稿 |
| 20〜22 分 | 回線 10G、10G スイッチ、電力契約、2U DB、2 本目のラック |
| 24 分〜 | スイッチ間の帯域が壁になる(集約スイッチと 10G アップリンクで組み直す) |

## 開発

```sh
npm install
npm run dev      # 開発サーバー
npm test         # シミュレーションのユニットテスト
npm run build    # 型チェック + dist/ へビルド(依存ライセンスの検査込み)
npm run preview  # ビルド結果の確認
npm run balance  # バランス確認ボット(BOT_MIN=20 などで時間指定、BOT_SAVE=1 で最後の状態をセーブとして出力)
```

### 調整値の場所

| 調整したいもの | 場所 |
| --- | --- |
| **価格まわり**(初期資金、全体の物価、機器・ラック・ケーブルの価格、維持費、解放・強化の価格と増加倍率) | `src/sim/pricing.ts` |
| スイッチ・ストレージの性能(U・消費電力・ポート・IOPS・処理能力) | `src/sim/catalog.ts` の `MODELS` |
| サーバのパーツの性能と電力(CPU のコア数ごとの電力、メモリ、ドライブの IOPS、NIC、シャーシのベイ数)、プリセット、最初の構成 | `src/sim/catalog.ts` の `CPU_OPTIONS` / `MEMORY_OPTIONS` / `DRIVES` / `NICS` / `CHASSIS` / `PRESETS` / `START_PARTS` |
| サーバのシャーシとパーツの価格、下取りの割合 | `src/sim/pricing.ts` の `CHASSIS_PRICES` / `CPU_PRICES` / `MEMORY_PRICE_PER_GB` / `DRIVE_PRICES` / `NIC_PRICES` / `PART_REFUND_RATE` |
| ラックの高さ・電力契約の段階、回線契約の速度 | `src/sim/config.ts` の `RACK` / `UPLINK_LEVELS_GBPS` |
| 共通の仕事量(db の読み書き・memcached・LB・ディスクの待ち時間) | `src/sim/config.ts` の `WORK` |
| サービスごとの仕事量・役割・始めたときのユーザー数・市場規模・単価(検索・配信・投稿の量) | `src/sim/config.ts` の `SERVICES` |
| ブログの画像投稿・コメントで増える仕事量 | `src/sim/config.ts` の `BLOG_FEATURES` |
| キャンペーンの長さ・クールタイム・倍率 | `src/sim/config.ts` の `CAMPAIGN`(価格は `pricing.ts` の `CAMPAIGN_PRICE`) |
| ケーブルの長さの計算 | `src/sim/config.ts` の `CABLE` |
| ユーザーの増え方・離脱 | `src/sim/config.ts`(`GROWTH_RATE`・`CHURN`) |
| 流量の揺れなどの難易度 | `src/sim/config.ts` の `DIFFICULTY`(既定はオフ) |
| メトリクスの保存期間・キャパシティの見積もり間隔と基準・予測の長さ | `src/sim/config.ts` の `METRICS` |
| 解放・強化の効果、段階、投資メニューのタブ | `src/sim/economy.ts` |
| VM の大きさ、オーバーコミット、移行で止まる時間、共有ストレージの IO | `src/sim/config.ts` の `VIRT` |
| レプリカの反映の負荷 | `src/sim/config.ts` の `REPLICATION` |
| 機能分割で 2 台目が持つ割合 | `src/sim/config.ts` の `DB_SPLIT` |
| CDN の当たる割合 | `src/sim/config.ts` の `CDN`(従量課金は `pricing.ts` の `CDN_PRICE_PER_GB`) |
| 回線を増やす工事費 | `src/sim/pricing.ts` の `LINE_PRICE` |
| Pod の大きさ・Pod で動かせる役割・Pod の数の上下限・オートスケールの目標と間隔 | `src/sim/config.ts` の `K8S` |

価格は「n 回目の価格 = first × growth^n × PRICE_SCALE」で決まる。変えたら `npm run balance` のログで節目の時刻を見比べる。

### 構成

```
src/
  sim/       描画に依存しないシミュレーション(テスト対象)
    catalog.ts     機種、サーバのシャーシ・パーツ・プリセット
    facility.ts    物理層: ラック・機器・ポート・ケーブル
    flow.ts        流量モデル: 経路、使用率、成功率、応答時間
    simulation.ts  時間・お金・ユーザー・操作・キャパシティの見積もり
    forecast.ts    需要予測(ロジスティック成長)
    metrics.ts     直近の集計と 1 秒ごとの推移
    economy.ts     投資・段階
    pricing.ts     価格・維持費
    save.ts        セーブ
  render/    PixiJS による列の立面図(前面・背面・配線・カメラ)
  ui/        詳細パネル・投資パネル・メトリクス(ダッシュボード)
  main.ts    画面のつなぎ込み
tests/       Vitest(npm test)
scripts/     バランス確認ボット(npm run balance)
```

### GitHub Pages で公開する

`main` に push すると、テスト・ビルドのあと自動で公開される(Settings → Pages の Source は「GitHub Actions」)。PR ではテストとビルドだけを実行する。
