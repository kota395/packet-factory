# packet-factory

データセンター/ネットワークを題材にした、ブラウザで遊べる「ライン自動化」ゲーム。
GitHub Pages などの静的ホスティングだけで動くことを前提にする。

> ステータス: 最小プロトタイプ(LB / WEB / DB、2 種類のリクエスト、1 ステージ)
>
> 技術選定とライセンス方針は [docs/tech-stack.md](docs/tech-stack.md) を参照。

## 開発

```sh
npm install
npm run dev      # 開発サーバー
npm test         # シミュレーションのユニットテスト
npm run build    # 型チェック + dist/ へビルド(依存ライセンスの検査込み)
npm run preview  # ビルド結果の確認
```

### GitHub Pages で公開する

公開先: https://kota395.github.io/packet-factory/

1. リポジトリの Settings → Pages で Source を「GitHub Actions」にする(初回のみ)
2. `main` に push すると、テスト・ビルドのあと自動で公開される

PR ではテストとビルドだけを実行する。

## 遊び方(プロトタイプ)

- 下のツールバーでノードを選び、空きマスをタップして配置する
- 「接続」で接続元 → 接続先の順にタップしてつなぐ(同じ線をもう一度つなぐと解除)
- 接続できる向き: NET → LB / WEB、LB → WEB / LB、WEB → DB
- ▶ で開始。ゲーム内 24 時間(実時間 5 分、早送り可)を可用性 99% 以上で乗り切ればクリア
- 「共有」で今の構成を URL としてコピーできる。構成はブラウザにも自動保存される

## コンセプト

工場ゲームの「ベルトコンベアと加工機」を「ネットワーク経路とサーバー群」に置き換えたもの。
流れてくるのは鉱石ではなくリクエスト(パケット)。プレイヤーはノードを配置・接続して、
増え続けるトラフィックを SLA を守りながら捌くインフラを設計する。

常に **スループット / レイテンシ / コスト** の 3 つがトレードオフになることを面白さの軸にする。

## コアループ

1. インターネット(画面左端)からリクエストが流れ込む
2. プレイヤーがノードを配置し、線でつないで経路を作る
3. 正しく処理できれば収益と SLA スコアを得る。詰まり・タイムアウト・エラーは失点
4. 収益で増設や新コンポーネントの解放を行い、より大きなトラフィックに挑む

## コンポーネント(候補)

| ノード | 役割・特性 |
| --- | --- |
| ロードバランサー | 振り分け方式を選べる(ラウンドロビン / 最少接続 / ハッシュ) |
| Web サーバー | CPU 上限と処理時間を持ち、溢れるとキューが伸びる |
| キャッシュ | ヒット率で後段の負荷を削減。容量超過で追い出しが発生 |
| DB | 書き込みが重い。リードレプリカを追加できるが、レプリケーション遅延がある |
| メッセージキュー | バーストを吸収するが、遅延は増える |
| CDN | 静的リクエストを手前で返す |
| WAF / ファイアウォール | 攻撃トラフィックを落とす(誤検知もある) |
| ストレージ | 容量と IOPS が別々に効く |

## リクエストの種類

色ごとに適切なルートが異なり、それがルーティング設計のパズルになる。

- 🔵 静的: CDN / キャッシュで返せる
- 🟢 API 読み込み: キャッシュが効くとは限らない
- 🟠 書き込み: DB のプライマリまで届ける必要がある
- 🟣 重いバッチ: キューに逃がすのが正解
- 🔴 攻撃・ボット: 通すと他のリクエストを巻き込む

## イベント・障害(候補)

- バズによるトラフィック急増
- DDoS 攻撃
- サーバー故障(冗長化していないと全停止)
- リージョン障害
- キャッシュ全消し(コールドスタート)
- メンテナンス枠(一時停止して入れ替えるタイミングを選ぶ)
- 機器の EOL(古い機材が使えなくなり移行が必要)

## 進行・ステージ

- 個人ブログ → EC サイト → SNS → 動画配信 → グローバルサービス
- 目標例: 「SLA 99.9% を維持しつつ、予算内でゲーム内 24 時間を乗り切る」
- クリア後にコスト・平均レイテンシ・可用性でランク付け

## UI 方針

- ノード上に CPU 使用率とキュー長のゲージ
- パケットは線上を流れる点として描画し、詰まると赤く溜まる
- 画面下部に p50 / p99 レイテンシ、エラー率、月額コストのミニグラフ(監視ダッシュボード風)
- 一時停止・早送り(設計を考える時間を確保)

## 技術的な前提

- サーバーなし(静的ファイルのみ)で完結させる
- シミュレーションは固定 tick の離散イベントモデル。各ノードは「処理能力・キュー・処理時間」を持つ待ち行列として扱う
- 大量トラフィック時はパケットを流量として集計し、描画だけサンプリングする
- 描画とシミュレーションを分離し、早送りやオフライン計算に対応しやすくする
- セーブは localStorage、構成の共有は JSON を URL ハッシュにエンコード

## 最初のプロトタイプ範囲

- ノード: LB / Web サーバー / DB の 3 種類
- リクエスト: 静的・書き込みの 2 色
- ステージ: トラフィックが徐々に増えるだけの 1 ステージ

「詰まりを見て増設する」手応えがあるかを確認してから、キャッシュや障害イベントを追加していく。
